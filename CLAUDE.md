# CLAUDE.md

Sweeter Side by Dachel: a café menu with online ordering, custom cake
bookings, and an in-store POS. Live at https://sweeterside.ph (`www.` and
`sweeterside.fly.dev` redirect there).

Read `claude/dev-status.md` first: it says what is shipped, what is live and
what is still open. The POS design is in `claude/pos-plan.md`, and setup and
behaviour are in `README.md`.

## Hard rules

- **Zero npm dependencies.** The app uses only Node built-ins: `node:http`,
  `node:sqlite` (`DatabaseSync`, WAL), `node:crypto` and `node:test`. Do not add
  packages or a build step. It needs Node 22.5 or later.
- **Strict CSP:**
  - No inline scripts: `script-src 'self'`.
  - Scripts live in their own files under `admin/` and `assets/js/`.
  - Inline `style` attributes are allowed (sprite crops and photo positions).
- **Money is integer centavos** (`*_cents` columns), everywhere in orders,
  lines, payments, refunds and shifts.
  - Menu prices, sale values and voucher values stay whole pesos, as the owner
    types them.
  - Orders read back still carry peso fields (`total`, `subtotal`…) for the
    checkout page.
  - Rounding is half-up, only at the points listed at the top of
    `server/pricing.js`.
- **Manila time:**
  - SQLite stores UTC (`datetime('now')`).
  - Use `server/clock.js` for Manila days and times (`manilaDate`,
    `manilaDateStartSql`, …).
- **The server is the authority.** Prices, totals, discounts and permissions
  are worked out on the server. The browser's numbers are never trusted.
  Every admin write needs the session plus the `X-CSRF-Token` header.
- **The tax status is non-VAT** (8% income tax option).
  - Never add the 8% to orders or receipts.
  - Keep the VAT-registered code path working; it is a settings switch.
- **Personal data:**
  - SC/PWD ID numbers are shown in full only to owner and cashier screens and
    the owner's CSV export.
  - They are masked (`****1234`) everywhere else.
  - Never send `pos_input` to the client.
  - Logs carry reason codes and ids, never names, phones or addresses.

## Layout

- `server/index.js`: routing, auth gates (`requireApiAuth`, `requireStaff`),
  static files.
- `server/db.js`: schema and migrations. Migrations must be additive or done
  in one transaction, safe on the live database, and must never rewrite
  existing orders except to convert units.
- `server/pricing.js`: the pure pricing engine, shared by the checkout and
  the POS.
- `server/pos.js`, `payments.js`, `shifts.js`, `reports.js`: the POS.
- `server/staff.js`: roles, PINs and overrides.
- `server/audit.js`: the append-only audit log.
- `admin/*.html` + `*.js`: admin pages. Each page loads `common.js` first; POS,
  Staff and Reports also load `staff-gate.js`.
- `templates/`: the customer pages. `index.html` is generated by the server;
  never edit it by hand.

## Roles and the POS

- **Roles:**
  - `owner`: everything.
  - `cashier`: orders, payments, discounts up to the limit.
  - `waiter`: dine-in only, send to kitchen.
- **Permissions** live in `staff.PERMISSIONS` and are enforced on the server.
  Anything over a role's limit needs an owner PIN override, which is audited.
- **Staff session:** a staff session (header `X-Staff-Token`) sits on top of
  the admin session.
  - A locked POS answers **423**.
  - A wrong PIN is **403 with `wrong_pin`**. Never 401: `common.js` takes 401
    to mean signed out.
- **Idempotency:** POS saves, payments and refunds carry a `request_key`.
  Tabs carry a `version`.

## Working conventions

- **Tests:** run `npm test` before every commit; all tests must pass. Add
  tests for new behaviour and for each bug fix. A bug-fix test should fail
  without the fix.
- **Running tests** rewrites `index.html`; run `git checkout -- index.html`
  afterwards.
- **Line endings:** the files use CRLF. Prefer the Edit tool for exact edits.
  Bash heredocs and `node -e` strings mangle backslashes, backticks and `${}`.
  For a multi-step edit, write a script to the scratchpad and run it.
- **Writing:** comments and UI text are in plain, short sentences, matching
  the existing code.
- **Local manual testing:**
  - Use a throwaway database: `PORT=3312 DB_PATH=<scratch>/app.db DATA_DIR=<scratch> node server/index.js`.
  - Create the admin with `ADMIN_PASSWORD=… node scripts/create-admin.js --email …`.
  - Static files are cached for 5 minutes. In the browser, refetch them with
    `{ cache: 'reload' }`.

## Git, PRs and deploying

- **Branches:** work on a feature branch, never directly on `main`. Commit in
  logical steps. End every commit message with the co-author line from the
  session.
- **Staging first, then live.** Every change goes through staging before the
  live site:
  1. Make the change on a feature branch and run `npm test`.
  2. Open a PR with `gh pr create`.
  3. Deploy that branch to staging (no need to ask), run the after-deploy
     checks there, and tell the user what to try on
     `https://staging.sweeterside.ph`.
  4. Wait. If the user asks for changes, push them to the same branch and
     deploy to staging again.
  5. When the user says "merge" or "merge and deploy", merge the PR. Then
     deploy `main` to live and to staging, so both run the same code.
  - Staging runs one branch at a time. Before deploying another branch
    there, say which one it replaces.
  - Never deploy to live from a branch, and never deploy to live what
    staging hasn't run, unless the user asks for an urgent live fix.
  - A change with a migration runs on staging first. The live backup with
    `VACUUM INTO` is still needed before the live deploy.
- **Stacked PRs:** do not merge them with `--delete-branch`. Deleting a base
  branch closes the PRs stacked on it. Retarget each to `main` first, or merge
  without deleting.
- **Deploy:** `"$HOME/.fly/bin/flyctl.exe" deploy --remote-only`. Quote the
  path: it contains a space.
  - Fly app `sweeterside`, region `sin`, volume at `/data` (`/data/app.db`).
  - Before any one-way migration, back up the live database on the volume
    with `VACUUM INTO` (run through `flyctl ssh console`).
- **Staging:** `https://staging.sweeterside.ph`, app `sweeterside-staging`.
  Deploy with `--config fly.staging.toml`. Pass `-a sweeterside-staging` to
  every other flyctl command for it. Never copy personal data there; use
  `scripts/staging-seed.js`.
- **After deploying:**
  - check `/healthz`;
  - check `flyctl status` (health check passing);
  - check `flyctl logs --no-tail` for errors.

  ## Security rules — apply to every change

This app handles customer personal data (names, PH phones, addresses, cake photos), staff PINs, payments, and Senior Citizen/PWD ID numbers (PH Data Privacy Act, RA 10173). Treat every change as security-relevant.

- **Zero npm dependencies.** Don't add packages. Use Node built-ins (`node:crypto`, `node:sqlite`).
- **SQL:** prepared statements with bound parameters only. Never build SQL with string concatenation or template literals; whitelist any dynamic column/sort names.
- **Output:** escape all data in HTML (server-rendered and the regenerated `index.html`). In browser JS use `textContent`/DOM APIs, never `innerHTML` with data. Neutralize CSV formula characters in exports.
- **CSP stays strict:** no inline scripts/styles, no `eval`, no new external origins without asking.
- **Every new endpoint:** auth + role check server-side, CSRF for state changes, body size limit, input validation, rate limit if public. Add it to the route table in `claude/security-audit.md`.
- **Never trust the client** for prices, totals, discounts, roles, stock, or order status. Recompute and validate on the server; enforce limits in DB transactions.
- **Client IP** comes only from the trusted Fly header (`Fly-Client-IP`), never raw `X-Forwarded-For`.
- **Uploads:** validate magic bytes, allow JPEG/PNG/WebP only, size limits, random filenames, strip EXIF, private files behind auth.
- **Secrets** only from env / `fly secrets`. Never hardcode, log, or commit them. Use `crypto.timingSafeEqual` for all secret comparisons.
- **Personal data:** collect only what's needed; mask SC/PWD IDs and phone numbers in lists; never put personal data in logs, errors, or URLs.
- **Errors:** generic messages to clients, details only in server logs.
- **Money:** integer centavos; validate quantities and amounts (no negatives, sane maximums).
- **Tests:** every security-relevant change gets a test (including a negative/attack test). Keep `npm test` green.
- **Before finishing any task:** re-check the diff against this list and mention any security implications in the summary. Flag anything that should be reviewed by a human.
